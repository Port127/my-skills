# 任务

## 触发约束

此 skill **仅通过显式调用触发**。

### ⛔ 不触发的场景
- 用户提到"交接"、"保存状态"、"新会话"等但未提及 context-handoff
- 会话结束前的自动保存或提醒
- 用户未显式引用 @context-handoff

### ✅ 触发条件
必须同时满足：
1. 用户明确说出"使用 context-handoff"或"启动 context-handoff"，或显式引用 @context-handoff
2. 用户提供了明确需求或上下文

将当前会话的工作状态、已完成的修改、发现的问题、待办事项和后续计划，
序列化为一篇结构化的 Markdown 文档。

**该文档的目标读者是另一个 AI agent**——新会话中的 AI 读取此文档后，
无需任何额外上下文即可无缝接续之前的工作。

**项目无关**：不假设任何特定目录结构、技术栈或文件命名约定。

## 输入参数

| 参数 | 说明 | 默认值 |
|------|------|--------|
| `--output <path>` | 输出文件路径（相对或绝对） | `docs/handoff-{YYYYMMDD-HHmm}.md` |
| `--mode` | 详细程度：`full` / `brief` / `plan` | `full` |
| `--include` | 额外包含的内容（如特定文件内容） | 无 |

## 执行步骤

### 1. 状态扫描

在生成交接文档之前，**必须**执行以下扫描，收集上下文信息：

#### 1a. 识别当前任务

检查：
- 最近的工具调用（文件读写、命令执行）
- 用户最近的指令
- 当前打开的文件
- 最近修改的文件
- 是否存在 todo list

推断：
- 用户的核心诉求是什么
- 当前在进行哪个子任务
- 任务完成度（未开始 / 进行中 / 即将完成）

#### 1b. 收集修改清单

- 运行 `git status` 获取未跟踪和已修改文件
- 运行 `git diff --stat` 获取变更摘要
- 运行 `git log --oneline -10` 获取最近提交
- 识别哪些文件是新创建的、哪些是被修改的

#### 1c. 识别问题和错误

- 回顾对话中是否遇到过错误、异常、意外行为
- 检查修复过的问题及其根因
- 识别尚未解决的遗留问题

#### 1d. 识别关键文件

- 当前打开的文件
- 最近读取/写入的文件
- git 状态中涉及的文件
- 对理解任务至关重要的配置文件、schema 文件等

### brief 模式

精简版，只包含核心信息：

```markdown
# Context Handoff — {YYYY-MM-DD HH:MM}

**任务**：{1 句话}
**进度**：{已完成 X/Y}
**当前在**：{正在做什么}

**已修改文件**：
- {path}: {做了什么}

**待办**：
- [ ] {下一步}
- [ ] {再下一步}

**注意**：{1-2 条关键提醒}
```

---

### plan 模式

只输出后续计划，适用于「工作分析完成，即将开始执行」的场景：

```markdown
# Execution Plan — {YYYY-MM-DD HH:MM}

## 目标
{1 句话}

## 执行步骤
| # | 步骤 | 涉及文件 | 预期结果 | 依赖 |
|---|------|---------|---------|------|
| 1 | ... | ... | ... | ... |

## 注意事项
- ...
```

1. 将文档写入 `--output` 指定的路径
2. 向用户展示摘要：

```
📋 交接文档已生成

路径：{output_path}
模式：{mode}
包含：
  - 任务状态：{是/否}
  - 用户意图：{是/否}
  - 已完成工作：{是/否}
  - 问题清单：{是/否}（{N} 个已解决, {M} 个待处理）
  - 关键文件：{是/否}（{N} 个）
  - 后续计划：{是/否}（{N} 个步骤）

```

## 给下一个 AI 的读取指令

当在新会话中读取交接文档时，应该：

1. **先完整读取文档**，理解上下文
2. **验证文档中列出的文件确实存在**（运行 `ls` 或 `git status`）
3. **确认当前状态与文档描述一致**（如有差异，先向用户报告）
4. **按「后续计划」逐步执行**，每完成一步向用户报告
5. **不要在未确认的情况下批量执行多个步骤**

---

## 硬约束

- MUST 先执行状态扫描（步骤 1），再生成文档
- MUST 包含 git 状态信息，即使项目没有 git 也要报告
- MUST 在文档中标注生成时间和模式
- MUST 区分「已完成」和「待办」，不要混淆
- MUST 列出所有最近修改过的文件，不要遗漏
- NEVER 编造未实际发生的操作或修改
- NEVER 在 brief 模式中省略「待办」事项
- NEVER 忽略用户在对话中提到的约束和偏好

## 注意事项

- 如果对话中没有明确的任务（用户只是闲聊），告知用户「当前没有进行中的任务」
- 如果项目没有 git，改用 `ls` 和时间戳判断文件变更
- 输出路径默认为 `docs/handoff-{timestamp}.md`，如果 `docs/` 目录不存在，使用 `./handoff-{timestamp}.md`
- 交接文档本身也应该可以被交接——如果新会话也需要交接，应读取旧的交接文档并合并到新文档中
- `--include` 参数可用于附加特定文件的内容到交接文档的「关键文件索引」部分（仅附加文件路径和简要说明，不附加完整内容）
