# Analyze Project

对软件项目进行系统性深度分析，产出言之有据的专业分析报告。

## 触发约束

此 skill **仅通过显式调用触发**。

### ⛔ 不触发的场景
- 用户提到"分析一下这个项目"、"看看代码"、"review"等但未提及 analyze-project
- 代码编写、bug 修复、功能开发过程中顺带的项目理解
- 用户未显式引用 @analyze-project

### ✅ 触发条件
必须同时满足：
1. 用户明确说出"使用 analyze-project"或"启动 analyze-project"，或显式引用 @analyze-project
2. 用户指定了目标项目路径或上下文

## 核心理念

分析报告的质量取决于三个要素：

1. **广度** — 覆盖足够多的分析维度，不遗漏关键方面
2. **深度** — 每个维度有代码级证据，不只是表面描述
3. **结构化** — 多份报告分层次组织，主报告导航 + 详情报告展开

输出不是"读了一遍代码后的感想"，而是基于事实的、可验证的、有结论的工程分析。

## 执行流程

整个分析分为 5 个 Phase，按顺序执行。Phase 1-2 中的子任务应尽量并行。

### Phase 1: 准备与项目探索

**目标**: 确定分析范围，加载分析方法论，初步了解项目全貌。

先读取方法论参考文件，再并行探索项目：

**步骤 A — 加载方法论** (直接读取，无需搜索)

读取 [references/analysis-methodology.md](references/analysis-methodology.md)。

该文件包含已固化的分析方法论：10 个核心分析维度、CHAOSS/OpenSSF/InfoQ 框架摘要、推荐报告结构、工具清单。不需要重新搜索网络获取这些内容。

**步骤 B — 项目初步探索** (使用 Agent, subagent_type: Explore)

快速扫描目标项目的全貌：

```
探索内容:
├─ 目录结构 (tree -L 3)
├─ README, LICENSE, CONTRIBUTING 等文档
├─ 配置文件 (package.json / requirements.txt / Cargo.toml / go.mod 等)
├─ 入口文件识别 (main / index / app)
├─ 技术栈初步判断
├─ Git 信息 (最近提交、贡献者、分支)
└─ 测试 / CI/CD / Docker 等基础设施
```

输出: 项目全貌结构化报告。

**两步完成后**，结合方法论的 10 个维度 + 项目特征确定：
- 分析报告的数量和主题 (通常 8-10 份)
- 每份报告覆盖哪些维度
- 需要深入阅读的核心源文件列表
- 项目类型 (Web/CLI/SDK/数据管道/GUI...) 决定是否需要专题报告

### Phase 2: 深度阅读与社区调研

**目标**: 获取代码级证据和社区外部视角。

并行执行两个子任务：

**子任务 A — 核心源码深度阅读** (使用 Agent, subagent_type: Explore)

逐一阅读 Phase 1 识别出的所有核心源文件。对每个文件记录：

```
记录维度:
├─ 关键类和函数
├─ 设计模式使用
├─ 模块间连接关系
├─ 值得注意的实现技巧
├─ 代码质量观察 (优点和问题)
└─ 潜在 bug 或技术债务
```

重点关注：
- 最复杂的模块 (通常行数最多、依赖最多)
- 核心业务逻辑的数据流
- 错误处理和边界情况
- 配置和扩展机制

**子任务 B — 在线社区调研** (使用 Agent, subagent_type: general-purpose)

读取 [references/community-research-guide.md](references/community-research-guide.md) 获取调研策略（平台列表、搜索词模板、结果组织方式），然后执行针对目标项目的社区调研。

该指南固化了"去哪里找、用什么搜索词、提取什么信息"的通用策略。具体的搜索结果因项目而异，需要运行时搜索获取。

```
调研内容 (参考 guide 中的详细策略):
├─ GitHub 数据 (stars, forks, issues, trending 历史)
├─ 中文平台覆盖 (知乎, CSDN, Bilibili, 掘金, V2EX...)
├─ 英文平台覆盖 (Reddit, HN, YouTube, Medium...)
├─ 作者背景和动机
├─ 教程、评测和推荐文章
├─ 与同类项目的对比
├─ 已知问题和用户反馈
└─ 衍生项目和 Fork
```

搜索策略: 中英文分别搜索，按 guide 中的搜索词模板组合关键词。

### Phase 3: 报告编写

**目标**: 将所有发现综合为结构化报告。

在用户指定的输出目录下，按项目名创建子目录存放报告。

默认输出路径: `{analysis_dir}/{项目名}/`

例如分析多个项目时的目录结构：

```
analysis/
├── AI_NovelGenerator/
│   ├── README.md
│   ├── 01-overview.md
│   └── ...
├── novel-plus/
│   ├── README.md
│   ├── 01-overview.md
│   └── ...
└── so-novel/
    ├── README.md
    └── ...
```

#### 报告体系

**主报告** `README.md`:
- 执行摘要 (项目一句话定位 + 关键发现表格)
- 综合评级 (多维度评分)
- 报告目录 (链接到所有详情报告)
- 分析方法论说明
- 项目快照表 (关键属性一览)

**详情报告** (编号 + 英文短名):

```
01-overview.md          — 项目概览
02-architecture.md      — 架构分析
03-modules.md           — 模块详解
04-core-logic.md        — 核心逻辑 (项目特定主题)
05-tech-stack.md        — 技术栈与依赖
...                     — 根据项目特征增减
NN-evaluation.md        — 评估与建议 (始终作为最后一份)
```

报告主题不是固定的。根据项目特征调整：
- Web 项目: 加 API 设计、前端架构、部署方案
- CLI 工具: 加命令行接口、插件机制
- SDK/库: 加公共 API 设计、版本策略、迁移指南
- 数据项目: 加数据流、ETL 管道、存储方案

每份报告的具体内容参考 [references/report-guide.md](references/report-guide.md)。

#### 写作原则

1. **言之有据** — 每个结论必须附带代码行号、文件路径或来源 URL
2. **代码片段** — 关键设计用简短代码片段说明，不要大段粘贴
3. **ASCII 图表** — 架构图、流程图、时序图使用 ASCII/Unicode 字符绘制
4. **表格对比** — 选型对比、竞品对比用表格呈现
5. **评分量化** — 尽可能给出数值评分或等级

#### 输出顺序

按以下顺序编写报告 (先写依赖关系最少的)：

```
第一批 (并行): README.md + 01-overview.md
第二批 (并行): 02-architecture.md + 03-modules.md + 05-tech-stack.md
第三批 (并行): 04-core-logic.md + 其他项目特定报告
最后一批:      NN-evaluation.md (需要前面所有报告的信息)
```

### Phase 4: 校验与交付

**目标**: 确认报告质量，交付最终成果。

检查清单：

```
完整性:
├─ 主报告包含执行摘要和目录
├─ 每份详情报告有明确主题
├─ 最后一份报告包含 SWOT 或综合评估
└─ 所有报告之间有交叉引用

证据性:
├─ 关键技术结论有代码行号或文件路径
├─ 社区数据有来源 URL
├─ 评分有评判依据
└─ 没有无根据的主观断言

可读性:
├─ 有 ASCII 图表辅助理解
├─ 表格用于对比场景
├─ 代码片段简短且有注释
└─ 中文技术术语保留英文原名
```

最终输出文件统计：
- 列出所有报告文件的路径、行数、大小
- 给出分析覆盖的维度汇总

### Phase 5: 总结

向用户展示：
1. 文件清单表格 (文件名 / 内容 / 行数 / 大小)
2. 关键发现摘要 (3-5 条最重要的结论)
3. 数据来源统计 (读了多少文件、搜索了多少来源)

## 并行策略

分析过程中大量使用并行 Agent 提升效率：

```
Phase 1: [读取方法论] + [项目探索]     ← 方法论从 references/ 加载，不搜索网络
Phase 2: [源码深读]   ‖ [社区调研]     ← 社区调研策略从 references/ 加载，具体数据运行时搜索
Phase 3: 报告编写 (按依赖顺序分批并行)
```

每个 Agent 的职责要明确，避免重复工作。Explore 类 Agent 负责代码阅读，general-purpose Agent 负责网络搜索和综合分析。方法论和社区调研策略已固化在 `references/` 中，不需要每次重新搜索。

## 常见问题处理

**项目很小 (< 10 个文件)**:
减少报告数量 (3-5 份)，合并模块和技术栈分析。

**项目很大 (> 100 个文件)**:
优先分析核心路径上的文件，非核心模块通过目录结构和命名推断。使用多个 Explore Agent 并行扫描不同子系统。

**无 README 或文档**:
从代码和配置文件推断项目目标。查看入口文件、CLI 帮助、测试用例获取使用方式。

**私有项目或无在线存在**:
跳过社区调研，将精力集中在代码分析上。

**非英语/非中文项目**:
根据项目主要语言调整搜索关键词。代码分析不受语言影响。
