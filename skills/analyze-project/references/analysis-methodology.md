# 项目分析方法论

> 综合 CHAOSS、OpenSSF、InfoQ、Mend.io、Google eng-practices 等 30+ 来源提炼。
> Skill 执行时直接读取本文件，无需重新搜索。

## 1. 主流分析框架

### 1.1 CHAOSS 框架 (Linux Foundation)

社区健康度量标准，40+ 指标分 5 类：

| 类别 | 关键指标 |
|------|----------|
| 社区活动 | 提交频率、Issue 量、PR 吞吐量、贡献者数 |
| 项目参与 | 首次响应时间、贡献者留存率、新人引导 |
| 社区支持 | Bug/CVE 解决时间、Issue 响应时间 |
| 项目可持续性 | 4 支柱: 社区、战略、治理、合规+安全 |
| 多样性 | 组织多样性、人口多样性、包容性指数 |

### 1.2 OpenSSF 评估指南

聚焦安全性和可持续性：
- 安全漏洞扫描
- 依赖溯源追踪
- 许可证合规验证
- 维护节奏分析
- 发布频率模式

### 1.3 InfoQ 五步分析法 (中文社区广泛采用)

1. **项目基础分析** — 目录结构、架构类型
2. **核心组件识别** — 按重要性排序模块
3. **模块深入分析** — 核心函数、数据流、流程图
4. **功能探索** — 从用户视角追踪功能到源码
5. **依赖关系分析** — 模块间依赖和关系

### 1.4 Mend.io SCA 框架 (软件组成分析)

4 支柱：
1. **可见性** — 所有开源组件的完整清单
2. **报告** — 安全漏洞、归属、清单记录
3. **修复** — 关键告警优先级、自动补丁
4. **合规** — 内部策略遵从、许可证要求

### 1.5 Google 工程实践

代码审查标准：
- 架构优于代码质量 ("well-written classes can't save a poorly structured system")
- 审查的首要目标是"确保整体代码健康在持续改善"
- 技术事实必须override个人偏好

## 2. 10 个核心分析维度

综合以上框架，一个全面的项目分析应覆盖以下维度：

| # | 维度 | 核心问题 |
|---|------|----------|
| 1 | 项目目标 | 解决什么问题？目标用户？价值主张？ |
| 2 | 技术栈 | 语言/框架/库/构建工具/基础设施 |
| 3 | 项目结构 | 目录布局、入口点、配置方式 |
| 4 | 架构与设计模式 | 架构风格、组件边界、数据流、扩展点 |
| 5 | 依赖与供应链 | 直接/传递依赖、安全性、许可证兼容性 |
| 6 | 代码质量 | 复杂度、测试覆盖、技术债务、文档 |
| 7 | 核心概念与领域模型 | 关键实体、术语、核心算法 |
| 8 | 核心逻辑与关键路径 | 执行流、并发模式、状态管理、容错 |
| 9 | 社区健康与治理 | 贡献者、响应时间、治理模式、发布节奏 |
| 10 | 使用方式与生态 | 安装方式、API 用法、集成点、插件生态 |

**不是所有维度都必须覆盖**。根据项目类型选择适用维度，不相关的可以跳过或合并。

### 维度覆盖矩阵模板

Phase 1 规划报告时和 Phase 4 验证时，使用以下矩阵追踪覆盖情况：

```
| 维度 | 覆盖报告 | 覆盖度 |
|------|---------|--------|
| #1 项目目标 | 01-overview | ✅ 完整 |
| #2 技术栈 | 05-tech-stack | ✅ 完整 |
| #3 项目结构 | 02-architecture, 03-modules | ✅ 完整 |
| #4 架构与设计模式 | 02-architecture | ✅ 完整 |
| #5 依赖与供应链 | 05-tech-stack | ✅/⚠️/❌ |
| #6 代码质量 | 03-modules, 09-evaluation | ✅/⚠️/❌ |
| #7 核心概念与领域模型 | {报告} | ✅/⚠️/❌ |
| #8 核心逻辑与关键路径 | {报告} | ✅/⚠️/❌ |
| #9 社区健康与治理 | 08-community | ✅/⚠️/❌ |
| #10 使用方式与生态 | {报告} | ✅/⚠️/❌ |
```

覆盖度说明：
- ✅ 完整：有专题报告深入覆盖
- ⚠️ 部分：在其他报告中附带提及，但不够深入
- ❌ 缺失：完全没有覆盖 — **必须补充**（追加到现有报告或新增专题）

## 2.5 项目类型分类学

不同项目类型需要不同的分析侧重和报告主题。Phase 1 探索后，先判断项目类型，再选择适配的分析策略。

| 类型 | 特征 | 核心资产 | 分析侧重 | 推荐专题报告 |
|------|------|---------|---------|-------------|
| **Web 应用** | 前后端、API、数据库 | 代码 + 架构 | API 设计、前端架构、部署方案 | API 设计、前端架构 |
| **CLI 工具** | 命令行、管道、插件 | 代码 + 命令系统 | 命令解析、插件机制、管道处理 | 命令系统、插件机制 |
| **SDK/库** | 公共 API、版本策略 | 代码 + API 设计 | 公共 API、版本策略、迁移指南 | API 设计、版本策略 |
| **数据管道** | ETL、存储、转换 | 代码 + 数据流 | 数据流、ETL 管道、存储方案 | 数据流、存储方案 |
| **GUI 应用** | 事件循环、渲染、组件 | 代码 + UI | 事件循环、渲染管线、状态管理 | UI 架构、状态管理 |
| **AI/LLM 多智能体** | Agent 管线、LLM 编排、状态治理 | 代码 + Prompt + 架构 | Agent 协调、Prompt 工程、上下文治理、质量门控 | Agent 系统、Prompt 工程、管线分析 |
| **Prompt/Skill** | Markdown 流程文档 + 提示词 | 知识 + Prompt | Prompt 设计、知识库、UX 流程 | Prompt 工程、方法论体系 |
| **游戏引擎** | 渲染、物理、资源 | 代码 + 引擎 | 渲染循环、物理模拟、资源管理 | 渲染管线、资源管理 |
| **混合型** | 跨 2+ 类型特征 | 多元 | 按主要 + 次要类型组合报告 | 按需组合 |

### 混合型项目处理

许多现代项目跨越多种类型。识别和处理混合型的规则：

**检测信号**:
- 项目同时有 CLI + Web UI + Library API
- 项目既是 AI/LLM 应用又有 Skill/Plugin 集成
- monorepo 中不同包属于不同类型

**处理策略**:
1. 确定 **主要类型** (占代码量/复杂度最大) 和 **次要类型**
2. 主要类型决定核心报告集 (01-05)
3. 次要类型增加专题报告 (06-08)
4. evaluation 评分维度取各类型推荐的并集 (去重后选 8-10 个)

**典型混合案例**:
- AI 创作工具 = AI/LLM 多智能体 + CLI + Web GUI + Skill → 加 Prompt 工程 + 多界面对比
- IDE 插件 = SDK/库 + GUI → 加 API 设计 + UI 架构
- 数据平台 = 数据管道 + Web + CLI → 加数据流 + API 设计
- **数据管道 + AI/LLM + CLI** = ETL 流水线 + LLM 集成 + 命令行界面 → 加流水线核心 + LLM/Prompt 工程 + 检索与向量 (如: 小说素材提取系统、AI 数据分析管道)

### AI/LLM 多智能体项目特别说明

这类项目是 2025-2026 年快速增长的新类别。核心分析维度：

1. **Agent 架构分析** — Agent 数量、角色分工、协调模式 (管线/图/层级)
2. **Prompt 工程分析** — 约束层次、上下文治理、规则栈、反偏差机制、提示词规模
3. **状态治理分析** — 真相文件/状态管理、CQRS、Event Sourcing、一致性保障
4. **质量门控分析** — 审计维度、质量门、回退/重试策略、温度递增
5. **LLM 供应链分析** — 模型依赖、服务商适配、成本模型、供应商锁定风险
6. **多界面分析** — CLI/TUI/Web/API 的统一 Action Surface 设计

#### LLM 流水线项目特别说明

当项目同时包含数据管道 + LLM 集成时（如小说素材提取、AI 数据分析），额外关注：

1. **流水线阶段分析** — 阶段数量、各阶段职责、阶段间数据传递格式、状态机定义
2. **断点续传设计** — 粒度 (章/批次/阶段)、状态存储 (sidecar JSON/YAML/DB)、恢复策略、并发控制 (lease/锁)
3. **容错降级策略** — 每个阶段的 LLM 失败兜底方案 (默认值/统计兜底/空结构)、是否有"降级真空"
4. **动态参数控制** — 根据流水线进度调整 LLM 参数 (temperature/max_tokens/thinking_budget)
5. **LLM 调用链** — 从 CLI 命令到 API 调用的完整路径、重试策略、错误分类、遥测系统
6. **成本模型** — 各阶段 Token 消耗估算、批量优化策略、断点续传的成本节省

#### 约束层次分析 (Constraint Hierarchy)

AI 项目控制 LLM 输出质量通常采用多层约束。分析时绘制约束层次图，评估各层的完备性和一致性：

```
Layer 1: Schema 约束 (最强 — JSON Schema / Pydantic 类型强制校验)
Layer 2: 协议约束 (中强 — 指令协议 set/append/done、输出格式约定)
Layer 3: 系统提示词规则 (中 — 行为规则、边界保护、禁止事项)
Layer 4: 上下文注入 (弱 — 事实子图、引用数据、章节上下文)
Layer 5: 运行时参数 (最弱 — temperature / max_tokens / top_p)
```

评估要点：
- 各层约束是否存在矛盾（如 Schema 要求必填但 prompt 未提示）
- 内层约束失败时外层能否兜底（如 Schema 校验失败 → 自动修复 prompt）
- 是否存在"约束真空"（某维度没有任何层覆盖）

#### Prompt 分布分析 (Prompt Distribution)

AI 项目的提示词通常分布在三个层次，分析时需全面盘点：

| 层次 | 存储位置 | 维护者 | 修改成本 | 可定制性 |
|------|---------|--------|---------|---------|
| **数据库/配置存储** | DB 表 / YAML / JSON | 用户/管理员 | 无需发版 | ✅ 用户可编辑 |
| **代码内嵌** | 源码中的字符串常量 | 开发者 | 需要发版 | ❌ 固定 |
| **动态组装** | 代码中运行时拼接 | 开发者 | 需要发版 | ⚠️ 部分可配 |

评估要点：
- 内嵌比例 — 内嵌 >50% 意味着修改行为规则需要完整开发流程
- 国际化就绪 — 内嵌硬编码是否为单一语言，是否阻碍 i18n
- 提示词版本管理 — 是否有变更历史、回退机制
- 提示词测试 — 修改后能否自动验证效果（A/B 测试框架）

### Prompt/Skill 项目特别说明

这类项目的核心资产不是代码，而是**知识体系**和**Prompt 设计**。分析时需要：

1. **知识密度分析** — 指南文档的技法覆盖度、示例丰富度、操作性
2. **Prompt 工程分析** — 提示词的约束设计、自驱机制、反偏差防御
3. **流程架构分析** — Phase/Step 的状态机设计、数据流、错误恢复
4. **多 Agent 协调分析** — 并行策略、任务分配、并发安全

| 测试覆盖 | coverage.py、Istanbul/nyc | 示例覆盖度 (每种技法是否有示例) |

### 状态层分析模式

对于数据密集型项目，需要深入分析状态管理架构。常见模式及其识别特征：

| 模式 | 识别特征 | 分析重点 |
|------|---------|---------|
| **CQRS** | 读写分离、命令/查询接口不同 | 写入路径 vs 读取路径、一致性保证 |
| **Event Sourcing** | 事件日志、状态可回溯、检查点 | 事件不可变性、状态推导效率 |
| **Reducer** | 纯函数、(state, action) → newState | 状态单调性、可测试性 |
| **真相文件 + 索引** | Markdown/JSON 权威 + SQLite/内存缓存 | 缓存失效策略、重建能力 |
| **乐观并发** | 版本号、冲突检测 | 冲突解决策略、用户感知 |

分析时绘制 **状态流转图**：数据从哪来 → 如何变换 → 存到哪去 → 如何读回。

## 5. 代码质量量化指标

Phase 3 分析和 Phase 4 验证时使用以下量化阈值：

### 5.1 God File 检测

| 指标 | 阈值 | 严重性 | 建议 |
|------|------|--------|------|
| 单文件 > 100KB | 严重 | 🔴 | 必须拆分 |
| 单文件 50-100KB | 警告 | 🟡 | 建议拆分或提取子模块 |
| 单文件 > 1000 行 | 警告 | 🟡 | 考虑拆分 |
| 函数 > 200 行 | 警告 | 🟡 | 上帝函数，建议分解 |
| 函数 > 500 行 | 严重 | 🔴 | 必须分解 |

**检测方法**: `find . -name "*.ts" -o -name "*.tsx" -o -name "*.js" | xargs wc -c | sort -rn | head -20`

### 5.2 技术债务编号

在 evaluation 报告中使用标准化编号：

| 前缀 | 类型 |
|------|------|
| `GOD-xx` | God File / 上帝函数 |
| `PROMPT-xx` | Prompt 工程问题 (仅 AI 项目) |
| `BUG-xx` | 确定的 bug |
| `DESIGN-xx` | 设计问题 |
| `PERF-xx` | 性能问题 |
| `SEC-xx` | 安全问题 |
| `STYLE-xx` | 代码风格 |
| `TEST-xx` | 测试缺失 |
| `DOC-xx` | 文档缺失 |
| `DEP-xx` | 依赖/供应链问题 |
| `TYPE-xx` | 类型安全问题 |

## 6. 10 条关键原则

1. **架构优先** — 软件质量从结构设计开始
2. **指标客观** — "技术事实必须override个人偏好"
3. **渐进理解** — 先广后深，不要试图一次理解所有
4. **追踪数据** — 从入口到出口追踪数据流是最佳理解策略
5. **测试即文档** — 测试套件是最可靠的活动文档
6. **先跑起来** — 能运行项目是最重要的第一步
7. **社区健康很重要** — 技术优秀但社区消亡的项目是风险
8. **依赖意识** — 开源占典型代码库 60-80%，必须系统分析
9. **安全默认** — 溯源、漏洞扫描、许可证合规不可省略
10. **持续改善** — 审查的首要目标是整体代码健康在改善
