# 社区调研策略

> 项目分析时"去哪里找、搜什么、提取什么"的通用策略。
> 具体的搜索结果因项目而异，需要运行时搜索。

---

## 1. 调研内容矩阵

| 维度 | 要提取的信息 |
|------|-------------|
| **GitHub 数据** | Stars/Forks/Watchers/Contributors/Issues/Releases、Trending 历史 |
| **作者/团队** | 背景、动机、其他项目、活跃度 |
| **社区覆盖** | 哪些平台有讨论、内容类型 (教程/评测/讨论)、语言分布 |
| **用户反馈** | 正面评价、负面评价、常见抱怨、功能请求 |
| **竞品对比** | 同类项目列表、差异化特性、市场定位 |
| **衍生生态** | Fork、衍生项目、集成案例 |
| **知名收录** | 是否被 GitHub Blog、InfoQ、知乎周刊等推荐 |

## 3. 搜索词策略

### 基础搜索

```
"{项目名}"                          — 精确匹配
"{项目名}" {作者名}                  — 带作者
"{项目名}" review OR 评测 OR 使用    — 评价类
"{项目名}" tutorial OR 教程          — 教程类
"{项目名}" alternative OR 替代品     — 竞品讨论
```

### 社区定向搜索

```
site:zhihu.com "{项目名}"
site:reddit.com "{项目名}"
site:v2ex.com "{项目名}"
site:csdn.net "{项目名}"
```

### 竞品搜索

```
"{项目名}" vs {竞品名}
"{项目类别}" open source alternatives
"{项目类别}" 开源 推荐
```

### Skill/Prompt 项目专属搜索

```
"{skill名}" smithery OR shyft OR mcpmarket     — Skill 市场覆盖
"{skill名}" Claude Code skill                   — 通用 Skill 搜索
"{skill名}" 实测 OR 投稿 OR 使用体验            — 用户实际使用案例
"{skill名}" fork OR 衍生 OR 二次开发            — 衍生项目
npx skills add {作者名}                         — 安装方式验证
```

## 3.5 名称混淆检测

搜索过程中，注意识别与目标项目**同名但不同**的其他项目。这在热门命名（如 "NovelForge"、"Aurora"、"Phoenix"）中很常见。

**检测信号**:
- 搜索结果中出现 2+ 个不同组织/作者的相似名称项目
- 搜索结果的项目描述与目标项目明显不同（如一个是开源工具，一个是商业软件）
- 同一关键词在不同平台指向完全不同的项目

**处理策略**:
1. 在调研报告中**明确标注**名称混淆问题，列出所有同名项目及其区别
2. 搜索时使用**消歧关键词**: `"{项目名}" + {作者名}` 或 `"{项目名}" + {编程语言/框架}` 来精确匹配
3. 评估混淆对项目**可发现性的影响**: 是否在搜索引擎/社区中被稀释
4. 在评估报告中**建议**作者添加区分标识 (如 description 中加 "(开源)" / 副品牌名 / GitHub Topics 优化)

**输出格式**:
```markdown
### 名称混淆问题 ⚠️
"{项目名}" 被 N 个不同项目使用:
1. {作者A}/{项目名} — {描述} (开源, {许可证})  ← 本项目
2. {公司B} {项目名} — {描述} (商业, ${价格})
3. {组织C}/{项目名} — {描述} ({场景})

影响: {评估对搜索引擎曝光/社区讨论的影响}
建议: {消歧建议}
```

## 4. 竞品对比框架

搜集竞品信息时，关注以下维度：

| 维度 | 对比内容 |
|------|----------|
| 规模 | Stars/用户量/下载量 |
| 技术栈 | 语言、框架、架构 |
| 功能 | 核心功能覆盖度 |
| 活跃度 | 最近提交、Issue 响应 |
| 差异化 | 独特卖点 |
| 定价 | 免费/开源/商业 |

## 5. 用户反馈分类

收集到的用户反馈分为：

```
正面反馈 (Positive)
├─ 功能赞颂
├─ 使用体验好评
└─ 推荐语

负面反馈 (Negative)
├─ Bug 报告
├─ 功能缺失
├─ 体验问题
└─ 性能抱怨

建议 (Suggestions)
├─ 功能请求
├─ 改进建议
└─ 集成需求
```

## 6. 调研结果组织

最终将调研结果组织为：

1. **GitHub 数据表格** — 核心指标一览
2. **社区覆盖地图** — 各平台覆盖度 + 内容类型
3. **用户反馈摘要** — 正面/负面/建议分类
4. **竞品对比表** — 多维度对比
5. **关键发现** — 3-5 条最重要的洞察
6. **数据来源统计** — 按类别统计来源数量 (见下方模板)

### 数据来源统计模板

```markdown
| 类别 | 来源数 | 平台 |
|------|--------|------|
| GitHub 数据 | N | 仓库、Issues、Releases、Contributors、Trendshift |
| 中文平台 | N+ | 知乎(N)、CSDN(N)、掘金(N)、Linux.do(N)、... |
| 英文平台 | N | Reddit(N)、HN(N)、Medium(N)、... |
| Skill 市场 | N | ClawHub、Claude Code Marketplaces、... |
| npm/包管理 | N | npmjs、yarnpkg、... |
| 竞品 | N | N 开源 + N 商业 |
| **总计** | **N+** | |
```

**质量指标**: 来源总数是调研深度的量化度量。
- < 10 来源: ⚠️ 调研偏浅，建议补充
- 10-25 来源: ✅ 基本充分
- 25-50 来源: ✅✅ 深入调研
- > 50 来源: ✅✅✅ 全面覆盖
