# 报告编写指南

每份详情报告应包含的内容维度。根据项目特征选择适用维度，不必全部覆盖。

---

## 通用结构

每份报告遵循统一的开头格式：

```markdown
# {编号} — {报告标题}

> **一句话说明本报告覆盖的内容**

---
```

---

## 01-overview.md — 项目概览

适用维度：

| 维度 | 说明 | 证据来源 |
|------|------|----------|
| 项目目标 | 解决什么问题、目标用户、核心价值 | README、入口文件、配置 |
| 市场定位 | 在同类产品/项目中的位置 | 网络搜索、GitHub 对比 |
| 发展历程 | 关键版本、里程碑、转折点 | Git log、Releases、Trending 记录 |
| 作者/团队 | 背景、动机、其他项目 | GitHub profile、社区讨论 |
| 许可证 | 类型、权利和义务、兼容性 | LICENSE 文件 |
| 关键数据 | Stars/Forks/Issues/Contributors | GitHub API 或页面 |

---

## 02-architecture.md — 架构分析

适用维度：

| 维度 | 说明 |
|------|------|
| 整体架构 | 分层、模块划分、ASCII 架构图 |
| 设计模式 | 识别并解释使用的设计模式 (适配器/工厂/观察者等) |
| 模块依赖关系 | 模块间调用关系图 |
| 数据流 | 从输入到输出的完整数据流 |
| 线程/并发模型 | 线程结构、锁机制、异步模式 |
| 持久化策略 | 文件组织、数据库、缓存 |
| 通信协议 | HTTP/gRPC/WebSocket/MQ 等 |

---

## 03-modules.md — 模块详解

适用维度：

| 维度 | 说明 |
|------|------|
| 模块全景图 | 目录树 + 行数 + 职责 |
| 逐模块分析 | 每个模块的类/函数、设计模式、关键实现 |
| 代码质量观察 | 每个模块的优点和潜在问题 |
| 模块间关系 | 谁调用谁、数据怎么流转 |

对核心模块 (最复杂/最关键) 给予更多篇幅。非核心模块可以合并说明。

| GUI 应用 | 事件循环、渲染管线、状态管理 |
| 数据管道 | ETL 流程、转换规则、容错机制 |
| 游戏引擎 | 渲染循环、物理模拟、资源管理 |

## NN-evaluation.md — 评估与建议

**始终作为最后一份报告**，因为需要综合前面所有报告的信息。

必须包含：

### SWOT 分析

用表格呈现 Strengths / Weaknesses / Opportunities / Threats，每条附详情说明。

### 问题清单

按优先级分类 (高/中/低)：

```markdown
| 编号 | 问题 | 位置 | 影响 | 建议修复 |
|------|------|------|------|----------|
| BUG-01 | ... | 文件:行号 | ... | ... |
```

编号约定：
- `BUG-xx` — 确定的 bug
- `DESIGN-xx` — 设计问题
- `PERF-xx` — 性能问题
- `SEC-xx` — 安全问题
- `STYLE-xx` — 代码风格
- `TEST-xx` — 测试缺失
- `DOC-xx` — 文档缺失

### 改进建议

按时间跨度分组：
- 短期 (1-3 个月): 必须修复的高优先级问题
- 中期 (3-6 个月): 架构优化和功能补充
- 长期 (6-12 个月): 战略方向

### 竞品差距分析

与同类项目对比，列出需要追赶的功能和自身独特优势。

### 综合评分

多维度评分表 (10 分制)，包含评分理由。

### 最终结论

对项目的一段总结性评价，包含：
- 项目定性 (一句话)
- 短中长期判断
- 对作者的建议
- 对使用者的建议

## ASCII 图表规范

报告中使用的图表类型和绘制方式：

### 架构图 — 方框 + 连线

```
┌──────────┐
│ Module A │
└────┬─────┘
     │
     ├──→ ┌──────────┐
     │    │ Module B │
     │    └──────────┘
     │
     └──→ ┌──────────┐
          │ Module C │
          └──────────┘
```

### 流程图 — 判断分支

```
         ┌──────────────┐
         │  条件判断?    │
         └──────┬───────┘
                │
       ┌────────┴────────┐
       │                 │
      Yes               No
       │                 │
┌──────┴──────┐  ┌──────┴──────┐
│ 路径 A      │  │ 路径 B      │
└─────────────┘  └─────────────┘
```

### 时序图 — 多参与者

```
用户    GUI    后端    LLM    数据库
 │      │      │      │      │
 │ 请求 │      │      │      │
 │─────→│      │      │      │
 │      │ 调用 │      │      │
 │      │─────→│      │      │
 │      │      │ 查询 │      │
 │      │      │─────→│      │
 │      │      │      │ 读取 │
 │      │      │      │─────→│
```

### 雷达图 — 文本替代

由于 Markdown 中无法绘制真正的雷达图，使用文本条形图：

```
技术深度    ████████░░  8/10
架构设计    ███████░░░  7/10
代码质量    ██████░░░░  6/10
```

### 表格对比

当需要对比 3+ 个选项时使用表格：

```markdown
| 特性 | 项目A | 项目B | 项目C |
|------|-------|-------|-------|
| 特性1 | ✅ | ❌ | ✅ |
| 特性2 | ⭐⭐⭐ | ⭐⭐ | ⭐⭐⭐⭐ |
```
