# 报告编写指南

每份详情报告应包含的内容维度。根据项目特征选择适用维度，不必全部覆盖。

---

## 通用结构

每份报告遵循统一的开头和结尾格式：

```markdown
# {编号} — {报告标题}

> **一句话说明本报告覆盖的内容**

> **相关报告**: [{编号A}]({filenameA}) · [{编号B}]({filenameB})

---

{报告正文}

---

*→ 继续阅读 [{下一篇}]({下一篇文件名}) {一句话说明}*
*→ 返回 [README.md](README.md) 查看报告总览*
```

> **结尾导航段** 确保报告不是孤岛。最后一行始终指向 README 主目录。

---

## 交叉引用规范

报告不是孤立的文档，而是一个互相链接的知识网络。

### 引用规则

1. **开头引用** — 每份报告开头标注 2-3 份最相关的报告（如上模板）
2. **正文跳转** — 讨论其他报告主题时插入跳转链接：
   ```markdown
   Agent 协作拓扑详见 [04-agent-system](04-agent-system.md)。
   ```
3. **避免断裂** — 不引用不存在的报告编号；不引用与当前主题无关的报告

### Phase 4 验证标准

- 每份详情报告至少有 2 处 `[文本](其他报告.md)` 格式的链接
- 所有链接目标文件存在
- README 的报告目录链接全部有效

---

## 报告间一致性规范

多份报告由同一分析流程产出，必须保证内部一致性。

### 术语一致

- Phase 1 确定项目术语表（如"Skill"不写成"技能"，"Agent"不写成"代理"）
- 所有报告使用相同术语，不混用

### 评分量表

统一使用 10 分制，分段含义：

| 分段 | 含义 |
|------|------|
| 9-10 | 业界领先 |
| 7-8 | 良好，有改进空间 |
| 5-6 | 基本满足，存在明显问题 |
| 3-4 | 不足，需要重大改进 |
| 1-2 | 严重缺陷 |

### 标记规范

统一使用以下标记：
- ✅ 通过/完成/存在
- ⚠️ 有风险/需注意
- ❌ 缺失/失败/问题

### 数据一致性

- 同一指标（stars 数、版本号、文件数）在各报告中数值必须相同
- 一份报告标为"优势"的不应在另一份标为"劣势"
- README 的评分摘要必须与 evaluation 报告的评分详情完全一致

### Feature Flags 分析模板 (如适用)

当项目使用 Feature Flags 控制功能开关时，绘制 Feature 矩阵：

```
┌─────────────────────────────────────────────────┐
│ feature-a ──── 启用功能 A                        │
│ feature-b ──── 启用功能 B (依赖 feature-a)      │
│                                                 │
│ 互斥约束: feature-a ↔ feature-c (compile_error!)│
└─────────────────────────────────────────────────┘

| 变体 | 启用特性 | 功能差异 | 适用场景 |
|------|---------|---------|---------|
| 完整版 | a + b | 全部功能 | 正式使用 |
| 精简版 | 仅 c  | 缺少 X/Y | 受限环境 |
```

### 技术迁移分析 (如适用)

如果项目经历了从语言 A 到语言 B 的完全重写，增加迁移对比：

```markdown
| 对比维度 | 原技术栈 | 新技术栈 | 胜出 |
|---------|---------|---------|------|
| 分发方式 | 需要运行时 | 单二进制 | ✅ 新 |
| 内存占用 | ~100MB | ~15MB | ✅ 新 |
| 并发模型 | GIL 限制 | 原生多线程 | ✅ 新 |
| 开发速度 | 快 | 中等 | ✅ 原 |
```

### 可发现性分析

项目名在搜索引擎中可能被同名异义内容压制（如 "novel-material" 被材料科学论文压制）。

**分析步骤**:
1. 在 Google/Bing 搜索项目名（带引号），观察前 3 页结果
2. 在 GitHub 搜索项目名，检查排名位置
3. 在目标社区平台搜索，评估覆盖度
4. 识别语义冲突（项目名是否被其他领域压制）

**评估指标**:

| 维度 | 评分标准 |
|------|---------|
| 项目名辨识度 | 搜索前 3 页是否出现本项目 |
| GitHub 搜索排名 | 精确搜索能否在前 5 个结果中找到 |
| 中文平台覆盖 | 至少 1 个平台有讨论/文章 |
| 英文平台覆盖 | 至少 1 个平台有讨论/文章 |

**改进建议方向**:
- 添加 GitHub Topics / 详细 description
- 添加消歧标签到项目名 (如 "novel-material-ai")
- 在主要社区平台发布介绍文章
- 考虑项目改名（极端情况）

## Prompt 工程报告 (AI/LLM 项目专用)

对于 AI/LLM 多智能体项目，强烈推荐增加一份 Prompt 工程专题报告。

### 分析维度

| 维度 | 分析内容 | 证据来源 |
|------|---------|---------|
| **约束层次** | Schema 约束 → 协议约束 → 系统提示词 → 上下文注入 → 运行时参数 (5 层从强到弱) | 提示词构建函数、校验逻辑 |
| **Prompt 分布** | 数据库存储 vs 代码内嵌 vs 动态组装的比例、维护成本、用户可定制性 | 搜索所有提示词来源 |
| **上下文治理** | 预算控制、优先级排序、压缩策略、POV 过滤 | context-transform / composer 模块 |
| **规则栈设计** | Hard/Soft/Diagnostic 分层、覆盖边缘 | RuleStack 相关代码 |
| **反偏差机制** | 守卫检测、疲劳词表、反检测模式、输出验证 | 守卫代码 + 检测模块 |
| **输出合约** | 结构化格式、解析 + 修复循环、重试策略 | 解析函数 + 错误处理 |
| **双语维护** | 多语言提示的维护成本、一致性保障；内嵌硬编码是否为单一语言 | 提示词中的多语言部分 |
| **提示词规模** | 总量 (KB)、文件分布、内嵌 vs 外置比例 | 文件大小统计 |
| **维度管理** | 审计/评估维度数量、膨胀趋势、稀释风险 | 审计维度列表 |

### Prompt 分布盘点方法

对于每个 AI 项目，应盘点提示词的三层分布：

```
Layer 1: 数据库/配置存储 — prompt_service.get_prompt_by_name(...)
Layer 2: 代码内嵌硬编码 — 源码中的多行字符串常量
Layer 3: 动态组装 — 代码中运行时拼接的模板

评估指标:
- 内嵌比例 (内嵌行数 / 总提示词行数)
- 修改成本 (修改一条规则需要几步)
- 国际化就绪度 (是否有硬编码自然语言)
```

### 报告结构建议

```
1. Prompt 架构总览 (层次图 + 分布饼图)
2. 约束层次分析 (5 层约束的完备性和一致性)
3. Prompt 分布盘点 (三层来源 + 规模统计)
4. 系统提示设计 (按会话/Agent 类型)
5. 规则栈机制 (分层 + 覆盖边缘)
6. 题材/领域画像系统
7. 上下文治理 (预算 + 压缩 + 过滤)
8. 反偏差/反检测机制
9. 输出合约与解析修复
10. 质量评估 + 改进建议
```

## 安全与隐私报告 (安全敏感项目专用)

当项目涉及用户隐私、凭证管理、Web 服务、数据采集时，增加一份安全专题报告。

创建条件（满足任一即创建）：
1. Phase 1 初步发现中包含 ≥ 2 个 🔴 CRITICAL 级安全问题
2. 涉及用户隐私数据采集（遥测、日志上报、用户画像）
3. Web 应用无认证或认证机制薄弱
4. 存在 SSL/TLS 配置问题（信任所有证书、弱加密套件）
5. 凭证管理不当（明文存储、硬编码密钥、配置文件暴露）

### 分析维度

| 维度 | 分析内容 | 证据来源 |
|------|---------|---------|
| **隐私保护** | 遥测数据采集范围、用户知情权、opt-out 机制 | 遥测代码、隐私政策 |
| **认证授权** | 认证方式、权限控制、会话管理 | 认证代码、配置 |
| **密码/凭证管理** | 存储方式（明文/哈希/加密）、传输安全 | 配置加载代码 |
| **网络安全** | SSL/TLS 配置、证书验证、端口绑定 | HTTP 客户端代码 |
| **输入校验** | SQL 注入、XSS、路径遍历防护 | 输入处理代码 |
| **供应链安全** | 第三方依赖风险、CDN SRI 校验 | 依赖配置、HTML |

### 报告结构建议

```
1. 安全问题总览
   - 表格：编号 / 严重性 / 问题 / 位置 / 影响
   - 整体安全评分（文本条形图）

2. 🔴 CRITICAL 问题详细分析（每个问题）
   - 问题描述 + 代码片段
   - 攻击场景（ASCII 流程图或步骤说明）
   - 修复建议

3. ⚠️ HIGH 问题详细分析

4. 隐私影响评估（如适用）
   - 数据采集清单（采集什么、发送到哪、用户是否知情）
   - 用户权利分析（知情权、opt-out、数据删除）

5. 安全加固建议（按优先级排序）
   - 短期（1-3 个月）：必须修复
   - 中期（3-6 个月）：建议改进
```

### 严重性分级标准

| 级别 | 定义 | 示例 |
|------|------|------|
| 🔴 CRITICAL | 可直接导致数据泄露或系统被控制 | 明文密码、SQL 注入、无认证 Web 服务、静默遥测采集 MAC |
| ⚠️ HIGH | 有潜在安全风险，需要攻击链 | 弱随机数、信息泄露、不安全的默认配置、CDN 无 SRI |
| 🟡 MED | 代码质量问题，可能引发安全问题 | 硬编码配置、不完整的输入校验、非 volatile 缓存 |

### 安全评估可视化模板

```
隐私保护    ██░░░░░░░░  2/10  (静默遥测 + 无 opt-out)
Web 安全    ██░░░░░░░░  2/10  (无认证 + 0.0.0.0 绑定)
凭证管理    ███░░░░░░░  3/10  (Cookie 明文 + 接口泄露)
网络安全    ████░░░░░░  4/10  (SSL 可关闭 + CDN 风险)
输入校验    ██████░░░░  6/10  (路径遍历防护 ✅)
```

## NN-evaluation.md — 评估与建议

**始终作为最后一份报告**，因为需要综合前面所有报告的信息。

必须包含：

### SWOT 分析

用表格呈现 Strengths / Weaknesses / Opportunities / Threats，每条附详情说明。

### 问题清单

按优先级分类 (高/中/低)：

```markdown
| 编号 | 问题 | 位置 | 影响 | 建议修复 |
|------|------|------|------|----------|
| BUG-01 | ... | 文件:行号 | ... | ... |
```

编号约定：
- `BUG-xx` — 确定的 bug
- `DESIGN-xx` — 设计问题
- `PERF-xx` — 性能问题
- `SEC-xx` — 安全问题
- `STYLE-xx` — 代码风格
- `TEST-xx` — 测试缺失
- `DOC-xx` — 文档缺失

### 改进建议

按时间跨度分组：
- 短期 (1-3 个月): 必须修复的高优先级问题
- 中期 (3-6 个月): 架构优化和功能补充
- 长期 (6-12 个月): 战略方向

### 竞品差距分析

与同类项目对比，列出需要追赶的功能和自身独特优势。

### 竞争定位象限图 (当有 3+ 竞品时使用)

使用 ASCII 象限图展示项目在赛道中的位置：

```
                    专用度 ↑
                       │
    ★ 目标项目         │  ● 竞品A
      (语言, N★)      │    (语言, N★)
                       │
  ─────────────────────┼──────────────────→ 通用度
                       │
                       │  ◆ 竞品B
                       │    (语言, N★)
```

选择对赛道最有意义的两个轴（如：专用度 vs 通用度、功能完整度 vs 维护活跃度、性能 vs 易用性）。

### 综合评分

多维度评分表 (10 分制)，包含评分理由。

**评分维度需根据项目类型适配**：

| 项目类型 | 推荐评分维度 (选择 8-10 个) |
|---------|---------------------------|
| 传统软件项目 | 架构设计、代码质量、测试覆盖、文档、安全性、性能、社区、可维护性、依赖管理、用户体验 |
| CLI 工具/下载器 | 架构设计、功能完整性、安全性、社区活跃度、可维护性、跨平台支持、文档质量、依赖管理、用户体验、创新性 |
| AI/LLM 多智能体 | 架构设计、代码质量、创新性、测试覆盖、Prompt 工程质量、社区健康、可维护性、生态整合、依赖管理、用户体验 |
| Prompt/Skill 项目 | 流程架构、方法论深度、Prompt 工程质量、文档体系、创新性、知识库覆盖度、社区生态、用户体验、质量控制、可扩展性 |
| SDK/库 | API 设计、文档质量、版本策略、向后兼容、测试覆盖、社区、性能、安全性、易用性、生态 |

> **关键原则**：不要用代码质量维度评估知识密集型项目。Prompt/Skill 项目的核心质量在 Prompt 设计和知识体系，不在代码。

### 最终结论

对项目的一段总结性评价，包含：
- 项目定性 (一句话)
- 短中长期判断
- 对作者的建议
- 对使用者的建议

## ASCII 图表规范

```

│ Module A │
└────┬─────┘
     │
     ├──→ ┌──────────┐
     │    │ Module B │
     │    └──────────┘
     │
     └──→ ┌──────────┐
          │ Module C │
          └──────────┘
```

### 流程图 — 判断分支

```
         ┌──────────────┐
         │  条件判断?    │
         └──────┬───────┘
                │
       ┌────────┴────────┐
       │                 │
```

### 雷达图 — 文本替代

由于 Markdown 中无法绘制真正的雷达图，使用文本条形图：

```

架构设计    ███████░░░  7/10

```
